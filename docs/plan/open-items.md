# Open items — flashdb

Single source of truth for every known open defect, fix, optimisation and desired feature. One row per actionable item; a row that two tickets describe cites both. `ID` is the owning ticket (`T-<n>`), or `PLAN-<slug>` where no ticket owns it. `Status` is `open`, `partial`, `implemented` or `closed`; `partial` names the missing piece, `closed` means a recorded decision settled it and no further work is pending. A number keeps its condition; an unmeasured claim says `unmeasured`, a missing number `unknown`.

Ticket bodies, measured evidence and fix contracts live in `.scratch/<ticket>/issues.md`; this file only indexes them.

## Critical path to an end-to-end win over sqlite/postgres

Ranking is **inference**; each rank names the measured fact it derives from. "On the path" means removing the item changes whether an external verdict can be positive; "off the path" means the measured external record shows it is not what decides the comparison.

**On the path, in order of leverage.**

1. **T-83** — derives from `82` §9.5 + `83`: the only rejected 200 rps windows are 4.7% scan requests at ~5.9 ms each (`5,750,442` bytes read over 9 reads), and the baselines answer the same 4.7% with `stock_movement_order` while flashdb's derived index silently held **0 entries** on that instance. The external verdict was measured with flashdb's own access path empty, so every other ranking below rests on a comparison that must be re-taken after this.
2. **T-84 + PLAN-device-floor** — derives from `82` §6 (device fsync p99 **9,821 us** against a 10 ms lag ceiling, flashdb the only arm failing a rung: 2 rejected windows of 5 blocks at 200 rps) and `STATUS` §4 (pacer WAL `fdatasync` tails 77-99 ms under compaction build I/O). The rung flashdb loses is the rung where its lag sits on the device floor while sqlite/postgres keep 0.15-0.9 ms. `PLAN-ceiling-reconciliation` is closed, so what remains is scoring the records under the one decided rule (T-84).
3. **T-76 + the barrier path** — derives from `82` §6/§8: flashdb's service p99 is 109,766-403,213 us (worst of the three arms, 11-41x the device fsync tail) and its per-request service p50 (3.6 ms) is above postgres's (2.2 ms) at `mean_group_size` 1.0; under the ladder a service breach counts against flashdb when a baseline holds the same level without one.
5. **PLAN-postgres-absent** — derives from the M1 records: the postgres 18.6 arm that carried half the external comparison is not installed today, so M5 cannot be re-run until it is, and no substitute engine may stand in for it.
6. **PLAN-sqlite-regime** — derives from `82` §7: sqlite ran at **4.039x** against flashdb's 12.546x, i.e. sqlite sustained 200 rps at a less demanding regime than the pre-registration demands, so its win on that rung is not yet a like-for-like result at >=10x.
7. **PLAN-powerloss-durability** — derives from `docs/engine.md` §Foreground commit and `82` §5: T5-T7 are conditioned on equal durability, and flashdb's `durability_observed` is `null`; if the barrier must be tightened, item 3's device floor worsens.
8. **PLAN-ten-seed** and **PLAN-concurrency-proof** — derive from `82` §9.6/§9.8: one seed x 5 blocks with unrecorded in-run frequency and an idle-box proof that does not detect the resident processes; this is a publication requirement for the external claim, not a mechanism that changes the ratio.
9. **PLAN-flashdb-oracle** — derives from `82` §6/§9.1: the correctness oracle was deferred on every flashdb block, so an external win is not yet backed by a read-back of the same instance.

**Off the path (measured as not decisive for the external comparison).**

- **Memory and footprint (T-10, T-11, T-31, PLAN-bloom-ram, PLAN-tile-fd)** — derives from `82` §6/§7: flashdb's engine peak was **61.4-62.9 MiB of 128** ("the cap did not bind") while serving a 1.57 GiB instance, and postgres's data directory is 16.401x, so there is no footprint leg on which the comparison is lost.
- **Write amplification and compaction (T-12, T-19, T-70, PLAN-compaction-budget-derived, PLAN-orphan-cleanup)** — derives from `82` §6: no verdict reads on reorganisation (the learned arm and the reorg/compaction metrics were not run); these are the M3 efficiency KPI, which ranks below sustained throughput in the author's ladder.
- **T-13 and PLAN-scale-instance / PLAN-regime-100gib** — derive from `82` §1/§9: open and recovery are outside the measured phase, and the scored instance is 12.25x, so neither changes the external rung arithmetic; both gate a large-scale claim, not this comparison.
- **Join-heavy workload and layout space (T-29, T-81, PLAN-l2-colocation, PLAN-request-surface)** — derives from `roadmap` §M2 and `81` §Unmeasured: the measured external win/loss comes from the win mix's per-region page size and the `order_no` index, and no L2 cost has ever been measured; the M2 gate is 2/4 and the recorded proposal defers the engine work.
