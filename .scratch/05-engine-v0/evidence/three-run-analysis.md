# 0a 三次运行的对比分析（2026-09-19）

三次运行，机器全程有渲染负载，但负载形态不同：

| 指标 | 运行 1（0a 首测） | 运行 2（0a-redo v4） | 稳定性 |
|---|---|---|---|
| 4K QD1 均值延迟 | 94 µs | **717 µs**（5.3× 恶化） | ✗ 差：单线程提交路径被 CPU 争用摧毁 |
| 4K QD32 IOPS | 96,733 | **205,237**（2.1× 反而更好） | ✗ 差：运行间 2× 波动 |
| 顺序带宽 | 820 MiB/s | 828 MiB/s | ✓ **稳定（1% 内）** |
| 16K QD32 | 38,606 | 43,626 | ~ 差 13% |
| 64K QD1 | 5,285 | 5,119 | ~ 差 2% |

## 结论

1. **带宽是唯一对 CPU 负载稳健的校准量**：两次运行 1% 内一致（820 / 828 MiB/s）。它是 IO-bound 测量，CPU 争用影响小。
2. **延迟常量必须等空闲**：QD1 单线程提交延迟对 CPU 争用极其敏感（94 → 717 µs）。所有"依赖链"类校准（`objective.md` 的锚定曲线）都需要空闲机器。
3. **QD32 IOPS 运行间 2× 波动**：渲染的 IO 阶段与 CPU 阶段交替，磁盘自由度随之波动。不可校准。
4. **守卫的 load1 判定部分误报**：本轮运行期间瞬时 idle = 70–79%（机器其实基本安静），但 load1 = 17（渲染的 ~17 个 D 态线程拖高了 1 分钟均值——loadavg 是滞后指标且把 D 态计入）。**守卫应改用瞬时 idle%（已是 78% = 安静）+ 对 fio 进程排除后的 CPU 差分**，而不是 load1。
5. 引擎设计的对应修正：**带宽常量可以现在就定（820–828 MiB/s）**；页大小曲线（4K=94 / 16K=106 / 64K=188）的绝对值待重测，但"更大读 = 更多传输时间"的方向物理成立。

## 对 `objective.md` 校准的落点

- 立即可用：顺序带宽 ≈ 820 MiB/s（本设备）。
- 空闲后重测：全部延迟常量、QD 缩放曲线、p99 尾。
